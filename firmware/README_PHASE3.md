# Paseo Passport 固件 — 三期说明（0.3.0-phase3）

在二期（四屏导航 + 审批 + 预置指令）之上完成设计文档 §10 的三期
范围：**按键语音全链路**——总览/结果屏按住 OK 录音 → 松手自动上传
硅基流动 ASR 转文字 → 确认屏核对 → 再按 OK 才发送。本期仍为
**编译级验收**（物理设备不在本机，未实机联调）。

## 按键语义重整（本期先行项，定版）

引入「按住 OK 说话」后，OK 键的按压必须只有一个含义。结论：

- **OK 按下并持续 ≥ 约 350 ms = 语音手势**（仅在 ONLINE 且处于
  总览/结果屏时武装）：达到阈值的瞬间开始录音（屏幕切到录音屏），
  松开结束录音并自动上传识别。**该次按压此后不再触发任何短按/
  长按动作**——实现上 UI 在按下沿开始跟踪这次按压，框架随后送来
  的 CLICK/LONG 一律吞掉；不足 350 ms 松开的轻点由 UI 亲手补发
  该屏的 OK 短按动作（总览→结果屏、结果屏→指令菜单），其框架
  CLICK 同样被吞掉恰好一次，避免双触发。
- **OK 长按（2000 ms 框架事件）自本期起无功能**：在任何屏都直接
  忽略。理由：按住 OK 只有「说话」一个含义，用户在任何屏按住
  OK 都不会误触破坏性动作（尤其待审批屏的驳回）。
- **二期长按 OK 的功能全部迁移到长按 DOWN**（见操作表）：总览
  进待审批、结果屏返回、待审批驳回、菜单不执行返回。代价是
  DOWN 长按原有的「跳移 5 行 / 滚动 10 行 / 跳到返回行」被让位
  （DOWN 短按仍逐行移动；UP 长按的跳移/滚动保持不变）。
- 待审批屏、指令菜单、确认屏**不武装语音**：这些屏上 OK 仍是
  普通短按键（批准/执行/发送），按住不触发录音。
- **开机 BOOT 窗口长按 OK 进配网不变**（上电后约 2.6 s 窗口，
  2000 ms 框架长按判定，在 station 模式启动前关闭；录音只在
  ONLINE 后可用，两者时序互斥）。

## 操作表（定版，全屏）

图例：短 = 短按（click），长 = 长按（2000 ms），按住 = 按下
持续 ≥350 ms 后松开（仅 OK 且仅总览/结果屏）。

### 总览屏
| 按键 | 行为 |
|---|---|
| UP 短 / 长 | 焦点上移 1 / 5 行 |
| DOWN 短 | 焦点下移 1 行 |
| DOWN 长 | 进待审批屏（无待审批时底部反馈一行提示） |
| OK 短 | 进结果屏（对焦点 agent 拉 timeline） |
| OK 按住 | 语音录音（目标 = 焦点 agent），松开自动识别 |
| OK 长 | 无功能 |

### 结果屏
| 按键 | 行为 |
|---|---|
| UP 短 / 长 | 文本上滚 1 / 10 行 |
| DOWN 短 | 文本下滚 1 行 |
| DOWN 长 | 返回总览屏 |
| OK 短 | 进指令菜单 |
| OK 按住 | 语音录音（目标 = 本屏 agent），松开自动识别 |
| OK 长 | 无功能 |

### 待审批屏
| 按键 | 行为 |
|---|---|
| UP 短 / 长 | 切换条目 / 跳到首条 |
| DOWN 短 | 切换条目（含末尾「← 返回总览」行） |
| DOWN 长 | **驳回**焦点条目（「返回」行上则回总览） |
| OK 短 | **批准**焦点条目（「返回」行上则回总览） |
| OK 长 | 无功能 |

审批报文与对账规则同二期（`agent_permission_response` 的
requestId 填权限请求自身 id；10 s 未见 resolved 事件自动
fetch_agents 对账）。

### 指令菜单（结果屏 OK 进入）
| 按键 | 行为 |
|---|---|
| UP 短 / 长 | 切换菜单项 / 跳 5 项 |
| DOWN 短 | 切换菜单项 |
| DOWN 长 | 不执行，直接返回结果屏 |
| OK 短 | 执行焦点项（清单同二期） |
| OK 长 | 无功能 |

### 录音屏（按住 OK 触发，临时屏）
| 按键 | 行为 |
|---|---|
| 松开 OK | 结束录音 → 自动上传 ASR |
| UP / DOWN 按下 | 取消录音（文件丢弃，回原屏） |
| 其余按键 | 忽略 |

录音中显示已录时长（x.x 秒 / 60）与实时电平条（峰值保持 +
衰减）。60 s 到限自动停录并照常走识别。

### 识别中（临时状态）
| 按键 | 行为 |
|---|---|
| UP / DOWN 按下 | 请求取消：HTTP 不中断，结果回来即丢弃 |
| 其余按键 | 忽略 |

### 语音确认屏（新屏）
| 按键 | 行为 |
|---|---|
| OK 短 | **发送**识别文字（规则见下） |
| UP / DOWN（短或长） | 作废，回发起录音的屏 |
| 10 s 无操作 | 自动作废并回原屏（屏上显示剩余秒数） |

屏上折行显示识别全文（超出一屏时提示「全文将完整发送」）与目标
（agent 标题，或「新建任务 (provider)」）。进入确认屏后 400 ms
内的 OK 事件被忽略，防止录音松手尾随的框架 CLICK 误发送。

## 语音链路

```
按住 OK（总览/结果，ONLINE）─350ms→ 录音屏
  ES8311 麦克风 → I2S/CodecDev 16 kHz 单声道 PCM（100 ms 分块）
  → 直写 /storage/rec.wav（先占位 44 B 头，停录后回填真实尺寸）
松开 OK → asr_client 流式 multipart 上传（2 KB 分块，不整文件入 RAM）
  POST <asr_ep>（默认 https://api.siliconflow.cn/v1/audio/transcriptions）
  Header: Authorization: Bearer <asr_key>（只进请求头，永不打日志）
  表单字段：file=rec.wav（audio/wav）、model=<asr_model>
  （默认 XingChenAGI/XingChenASR-V3.2-Ultra）；超时 20 s；
  TLS 用内置 CA 证书包校验
→ 200 响应轻量解析取 "text"（支持 \uXXXX 转义）→ 确认屏
→ OK 发送 / 上下作废 / 10 s 超时作废
```

- 发送目标规则（确认时定，发送时再校验）：结果屏发起 → 本屏
  agent（`send_agent_message_request`）；总览发起 → 焦点 agent；
  无任何 agent 且 NVS 的 `def_prov`+`def_cwd` 齐备 → 以识别文字
  作 initialPrompt 走 `agent.create.request`；两者皆无 → 底部
  反馈「无发送目标」并留在确认屏。发送成功后回总览并立即
  `fetch_agents` 刷新一次；受理结果走二期 outbox 反馈行
  （「指令已受理」/「已新建 agent」/失败原因）。
- 录音文件在上传后（成败皆然）立即删除；取消亦删。录音短于
  100 ms 判「录音太短」不上传。ASR 失败（HTTP 非 200 / 超时 /
  空文本）给一行反馈并回原屏，不留重试副本。
- 防重入：录音/识别期间除「取消」外的按键全部忽略；语音任务
  （`paseo_voice`，栈 12 KB）串行处理整条链路，UI 任务不阻塞。
  离开 ONLINE（WiFi 断开）时 Hide 会取消在途录音，其迟到结果
  被静默丢弃。
- 实现结构：`components/asr_client`（纯 C，HTTP/JSON 解析，无
  NVS 依赖，端点/模型/Key 由调用方传入）；`main/paseo_voice.cc`
  （SPIFFS 挂载 + 录音/ASR 任务 + 结果队列）；按键手势状态机在
  `main/paseo_ui.cc`；板级新增三键的 press-down/up 转发
  （`ai_passport_board.cc`，无钩子时为 no-op，不改变旧行为）。

## 分区与 NVS 变化

- **分区表变更**（`partitions/v2/8m.csv`）：删除 `ota_1`（本固件
  OTA 本就禁用、只走整包刷机），其 0x2F0000 空间改为新增数据
  分区 **`storage`（SPIFFS，0x310000，0x2F0000 ≈ 3 MB）** 存放
  录音文件；`ota_0`、`assets`（0x600000/2M）偏移与大小不变。
  60 s 录音约 1.9 MB，分区余量充足。SPIFFS 首次挂载自动格式化。
  **刷本期固件必须整包刷写**（0x0 写入整包 bin），只刷 app 分区
  会因分区表不一致无法挂载 storage；整包刷写照例清掉旧 NVS，
  需重新配网。
- **NVS 无新增键**：ASR 沿用一期配网页已收集的 `asr_ep` /
  `asr_model` / `asr_key`（命名空间 `paseo`），本期开始真正调用；
  `def_prov` / `def_cwd` 兼作语音新建任务的默认值。

## 内存与双 TLS 并发

构建后静态占用（`idf.py size`，本期实测）：

| 项 | 数值 |
|---|---|
| 应用 xiaozhi.bin | 2,108,928 B（分区 0x2F0000，余约 31%） |
| DRAM 静态（.text+.bss+.data） | 105,780 / 321,296 B（32.9%），静态剩余 215,516 B |
| Flash 代码 / 数据 | 1,318,052 / 720,544 B |

- 并发结论（设计判定，**未实机验证**）：ASR 上传期间**不挂断
  relay WSS**。依据：(1) sdkconfig 已启用 mbedTLS 动态缓冲
  （`CONFIG_MBEDTLS_DYNAMIC_BUFFER=y` 等一期既有配置），单路 TLS
  会话的常驻内存远低于静态缓冲模式；(2) relay 的 10 s 应用层
  ping 与收发都在 paseo_client 自己的任务上，语音任务阻塞在
  HTTP 上不会饿死它；(3) 215 KB 级静态剩余堆应付第二路 TLS
  握手峰值（典型数十 KB）有余量。
- 降级路径已内建：若实机发现堆峰值不足，失败只会发生在
  `esp_http_client_open` 阶段 → 屏上反馈「识别失败：connect
  failed」，relay 连接与录音文件流程不受影响，可直接重试；
  届时再考虑「ASR 前挂起 relay、传完重连」的硬降级（本期未做）。

## 与二期的差异

- 按键：新增三键 press-down/up 转发；OK 短按在总览/结果屏改为
  UI 手势跟踪（轻点补发、长压吞掉）；OK 长按全面退役，其功能
  迁至 DOWN 长按（见操作表）。
- 屏幕：四屏 → 五屏（新增语音确认屏）+ 录音/识别中临时屏。
- 客户端协议面无变化（仍为二期子集）；新增的只是本地音频与
  ASR HTTP 通路，daemon 侧零改动。
- 应用版本串 0.2.0 → 0.3.0；一、二期整包保留在 dist 不覆盖。

## 已知限制

- 编译级验收：录音通路（ES8311 输入使能时序、InputData 阻塞
  读、电平计算）、SPIFFS 首次格式化、双 TLS 堆峰值、ASR 真网
  延迟均未实机验证。首次实机验收点（设计文档三期标准）：实机
  语音指令被 daemon 执行并在结果屏回显摘要。
- 录音格式固定 WAV/PCM 16 kHz 单声道（约 32 KB/s）：硅基流动
  接口实测可收；若日后换不支持 WAV 的 ASR，需另加编码环节。
- ASR 文本在客户端截断上限 1024 B（确认屏与发送一致）；超长
  识别结果会被截断发送。
- 确认屏不提供改字/重录：识别错了只能作废重说（上下键）。
- 识别中取消不中断在途 HTTP：UI 立即回原屏、结果回来即丢弃，
  但语音任务在后台仍被这次请求占用（最长 20 s 超时），期间
  新的按住录音会被拒（反馈「录音启动失败」）。
- SPIFFS 无磨损均衡且录音文件高频重写同一路径：桌面遥控的
  使用强度下可接受，长期高频使用建议观察。
- 报文子集与 daemon v0.12.0 对齐（一期纪律延续）。

## 构建与产物

```sh
source ~/esp/esp-idf-v6.0.1/export.sh
cd firmware
idf.py reconfigure   # 本期新增组件 asr_client 后需要
idf.py build
cd build
python3 -m esptool --chip esp32c3 merge_bin -o ../dist/Paseo-Passport-0.3.0-phase3-full.bin @flash_args
```

本期产物（2026-10-22 构建）：应用 xiaozhi.bin 2,108,928 B；
整包 7,664,505 B（0x74f379），md5 `e15f63938ee9e7830a13c1f3e7c4afaf`。
构建日志 `build_phase3.log`（含 BUILD_EXIT:0；首轮有一处
-Werror=format-truncation，已修）。

刷机（**必须整包**，分区表已变）：
`esptool.py --chip esp32c3 write_flash 0x0 dist/Paseo-Passport-0.3.0-phase3-full.bin`
（会清掉旧 NVS 配置，需重新配网；配网时 ASR Key 记得一并填上，
一期已填过的也需重填。）
