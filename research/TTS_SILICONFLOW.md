# 硅基流动 TTS 实测（Paseo Passport V2 TTS 章节依据）

- 实测时间：2026-10-22 晚（本 VM 经代理出网，时延为量级参考，真机走家庭 WiFi 会不同）
- 凭证：连接 custom.siliconflow（保险库），脚本 /tmp/sf_tts_test.py（dynamic_credentials 代理头、禁重定向）
- 测试句：「你好，我是你的专属会话，测试完成了。」（18 字，合成语音时长约 3.4 秒）
- 合成调用共 5 次（任务上限 6 次）

## 结论速览

- `FunAudioLLM/CosyVoice2-0.5B` 可用，系统音色名 `FunAudioLLM/CosyVoice2-0.5B:alex` 直接填 voice 即返回 200，**不需要先建自定义音色**。
- wav / mp3 / pcm 三种格式实测 200；**opus 返回 500 不可用**。
- 返回为 chunked 分块传输、无 Content-Length；但首字节耗时 4.3–9.4 秒，与总耗时接近——服务端合成占绝对大头，流式并不能让设备“早开口”，只能边下边播省内存。
- 计费无从 API 核实：/v1/user/info 已下线（410）。

## 接口与参数（仅实测通过的组合）

| 项 | 值 |
|---|---|
| 端点 | POST https://api.siliconflow.cn/v1/audio/speech |
| Content-Type | application/json |
| model | `FunAudioLLM/CosyVoice2-0.5B` |
| input | 待合成文本（UTF-8 中文原样） |
| voice | `FunAudioLLM/CosyVoice2-0.5B:alex`（系统音色，`<模型名>:<音色名>` 形态） |
| response_format | `wav` / `mp3` / `pcm`（见下表） |

请求体只需以上字段即可 200；未实测 speed/gain/sample_rate 等可选字段，固件首版不要依赖。

## 格式对比（同一句，18 字 ≈ 3.4 秒语音）

| 格式 | 返回 Content-Type | 字节数 | 时长 | 规格 | 折算 |
|---|---|---|---|---|---|
| wav | audio/wav | 161,454（复测 165,294） | 3.36s（复测 3.44s） | PCM s16le、24kHz、单声道 | ≈48KB/秒语音 |
| mp3 | audio/mpeg | 55,807 | 3.41s | 24kHz、单声道、约 131kbps | ≈16KB/秒语音 |
| pcm | application/octet-stream | 172,800 | 3.60s（按 24kHz/16bit/单声道推算，裸流无头） | 裸 PCM | 48KB/秒语音 |
| opus | — | HTTP 500（code 50507，耗时 23.1s 后报错） | — | — | 不可用，弃用 |

注：每次合成的语音时长有轻微随机性（同句同格式两次 wav 分别 3.36s/3.44s）。按字折算：mp3 约 3.1KB/字，wav/pcm 约 9–9.6KB/字；一段 100 字的回复约 19 秒语音、mp3 约 310KB、pcm 约 950KB。

## 时延与流式（同一句，每次全程计时）

| 调用 | 响应头到达 | 首个数据块 | 全部收完 |
|---|---|---|---|
| wav 第 1 次 | 9.36s | 9.39s | 10.32s |
| wav 第 2 次 | 4.26s | 4.29s | 4.98s |
| mp3 | 7.45s | 7.48s | 7.91s |
| pcm | 5.86s | 5.88s | 8.65s |

- 响应头为 `Transfer-Encoding: chunked`、无 Content-Length，数据确实分块渐进到达（pcm 一次在首块后又传了约 2.8s）。
- 但首块几乎与响应头同时到达、且响应头本身要等 4–9 秒：**服务端是近乎整句合成完才开始吐数据**。对固件的含义：不要指望靠流式把首播时延压到亚秒级；流式的真实价值是 pcm 可以边收边喂 I2S、不必整段落盘/进内存。
- 两次 wav 首字节 9.4s vs 4.3s，服务端时延抖动大，固件需按“短句也要等数秒”做交互预期（表情/字幕先行，语音随后）。

## 计费线索

- 调用前后各查一次 GET /v1/user/info：均返回 **HTTP 410**，body 为 code 20092 “This endpoint is deprecated and is no longer available.”——该接口已下线，无任何余额字段可比对。
- 与此前 ASR 实测结论一致：这个 Key 能调通，但是否扣费、余额多少无法经 API 核实，需 Leon 在硅基流动控制台侧确认。

## 给固件的建议

1. **格式选 pcm**：24kHz/16bit/单声道裸流，与板载 ES8311 直喂 I2S 的形态正合——免解码器（省 C3 的代码与 RAM）、免落盘；chunked 到达一块播一块。wav 内容与 pcm 相同、只多一个头，无优势；mp3 体积只有 1/3 但要引入 mp3 解码（代码+解码 RAM），且整段合成时延不变，仅在“必须整段下载再播”的备选路径才有意义。
2. **按句合成、流水线播报**：整段回复一次合成，首播要等整段生成（百字级回复首字节时延只会比短句的 4–9s 更久）。按句切分逐句请求：播第 N 句时预取第 N+1 句，听感连续且每句体积可控（短句 pcm 约 170KB 量级、mp3 约 56KB 量级）。
3. **打断实现**：朗读中打断 = 立即中止当前 HTTP 下载并停 I2S 输出、丢弃预取队列；chunked 流天然可弃，不需要服务端配合。
4. **时延预期写进交互设计**：发请求后先切“说话/思考”表情与字幕，语音在数秒后跟上是常态而非故障；超时与重试阈值按 ≥15s 设，避免把慢合成误判为失败（opus 那次 23s 才报错即是例证）。
5. opus 不要用（实测 500）；若日后要省流量再评估 mp3 解码方案。
